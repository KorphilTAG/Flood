# Feature spec

- Slug: critic-output-validator
- Feature: A rule-checking post-processing layer inside `ingestion/critic/` that independently verifies every AAR chunk-ID citation a critique response contains — both in the structured `chunk_ids` fields and inline in free-text `text` fields — actually belongs to that request's own retrieval set, and triggers bounded regeneration (not a silent pass-through, not an immediate error) when a citation fails that check.
- Status: draft
- Product refs: PRD 6.6 ("Output validator: a post-processing step run on every LLM output... that rejects any response referencing a chunk ID or feature ID not present in the corpus or the current impact JSON. Rejected outputs are regenerated, not passed through silently."); PRD 7 principle 3 (every LLM claim cites a real ID; non-compliant outputs "rejected... and regenerated"); PRD 11 Risks ("this only checks that a cited ID exists; it does not check that the citation is actually relevant... RAGAS... catches that gap — the validator and RAGAS check different failure modes"); FeatureBreakdown "RAG + Human/Landscape Data" track, step 6 ("Build the safety check that rejects any AI response that references something that doesn't actually exist in the historical library or the current flood facts. Built as a rule-checking layer inside the same FastAPI service from step 5 — no separate new tool.") and step 7 (RAGAS, explicitly a separate, later check of relevance not existence); architecture.md 5.7 ("Validator: a post-processing step that rejects any output referencing a chunk ID or feature ID not present in the corpus or the current impact JSON. Rejected outputs are regenerated, not passed through."); `pipeline/features/historical-critic-api/spec.md` and `changes.md` (the FastAPI/LangChain critic service this feature adds its rule-checking layer inside of, per FeatureBreakdown's own instruction that step 6 is "no separate new tool"); `ingestion/critic/schemas.py`, `llm.py`, `service.py`, `app.py`, `prompts.py`, `settings.py` (the actual code read to determine what already exists vs. the real remaining gap — see Problem).

## Problem

FeatureBreakdown's RAG track step 6 asks for "the safety check that rejects any AI response that references something that doesn't actually exist in the historical library or the current flood facts," built as rule-checking logic inside the same FastAPI service the critic (step 5, `pipeline/features/historical-critic-api`) already runs in. Reading that feature's actual code shows most of this request is already done, and it is important to say that honestly rather than re-describe finished work as new scope.

**What already exists (`ingestion/critic/schemas.py::build_structured_response_schema`, called from `service.py::run_critique`).** Every `POST /v1/critique` call retrieves a set of AAR chunks via `aar.search.search_index`, then builds a fresh Pydantic model *per request* whose `chunk_ids` fields on every objection/alternative are typed as `list[Enum]`, where the `Enum` contains exactly that request's retrieved `chunk_id`s (`ingestion/critic/schemas.py:88-116`). `llm.py::generate_critique` passes this per-request schema to `ChatOpenAI(...).with_structured_output(response_schema)`. This means the model's own structured output for the `chunk_ids` fields cannot represent a chunk ID it was not just handed as retrieval context — if it tries, Pydantic validation fails and `service.py` wraps the failure in `CritiqueGenerationError`, which `app.py` maps to a `502`. **This already covers "a cited chunk_id actually exists in the corpus the request retrieved from" for the structured `chunk_ids` field, and it already fails closed (never a 200 with a fabricated ID) when that constraint is violated.**

**What does not exist — the real gaps this feature closes:**

1. **No independent, rule-based re-check of the structured `chunk_ids` field.** The entire existence guarantee today rests on trusting that `langchain_openai`'s `.with_structured_output(...)` correctly enforces the dynamically-built `Enum` against the live OpenAI API. `historical-critic-api/changes.md`'s own "Residual risk" section states this exact path "was never made [tested] against the live OpenAI API" — only verified in isolation with plain Pydantic. A safety check that is *itself* only as strong as an unverified assumption about a third-party library's structured-output enforcement is not yet the independent backstop FeatureBreakdown step 6 and PRD 7 principle 3 ask for.
2. **No check at all on inline citations inside free-text `text` fields.** `prompts.py::build_human_message` instructs the model to "cite only these [chunks], by their exact chunk ID in brackets," and every retrieved chunk is rendered to the model as `[chunk_id] excerpt (...)`. Nothing stops the model from writing a bracketed chunk-ID-looking token *inside* an objection's or alternative's free-text `text` string (e.g., `"...as in [WIM-2015-07] officials waited too long..."`) that was never retrieved for this request. The schema-level `Enum` constrains only the structured `chunk_ids` array field — it does not, and structurally cannot, constrain arbitrary substrings of a free-text field. This is a real way for "a response that references something that doesn't actually exist in the historical library" to reach a caller today.
3. **No regeneration.** PRD 6.6 and architecture 5.7 both specify the validator's behavior as reject-then-regenerate: "Rejected outputs are regenerated, not passed through silently." Today, any structured-output/schema failure (including the Enum violation in gap 1, if it ever occurs) is wrapped once into `CritiqueGenerationError` and surfaced to the caller as a `502` — there is no retry, no regeneration attempt, no corrective feedback to the model. This satisfies "not passed through silently" but not "regenerated."
4. **"Current flood facts."** Per PRD 8 contract 2 and architecture 5.4, the concept this refers to is the impact extractor's impact JSON (feature IDs for roads/crossings/structures/camps, keyed to simulation time `t`). No impact extractor, no impact JSON schema, and no feature-ID producer exists anywhere in this repository yet — `historical-critic-api/spec.md`'s own Out of scope and Assumptions sections confirm this explicitly, and no feature folder in `pipeline/features/` builds it. There is nothing for a validator to check feature-ID citations against today. This spec states that plainly rather than inventing an impact-JSON integration that has no producer, matching the instruction under which this spec was written.

This feature therefore scopes narrowly to closing gaps 1–3 above (an independent rule-check of both citation surfaces, plus bounded regenerate-on-reject), inside the same `ingestion/critic/` FastAPI service, and states gap 4 as a documented non-goal rather than manufactured scope.

## In scope

1. A new module `ingestion/critic/validator.py` with a pure, deterministic rule-checker (no LLM call, no network call) that takes a parsed structured critique (the `objections`/`alternatives` lists, each with `text` and `chunk_ids`) and the set of `chunk_id`s retrieved for that request, and returns every citation violation found (empty list = passes):
   - **Structural re-check (independent of the schema Enum):** for every objection/alternative, every entry in `chunk_ids` must be a member of the retrieved-chunk-ID set for this request. This is a deliberate second, independently-testable check of the same fact the schema Enum is supposed to already guarantee (closing gap 1) — it does not replace or remove the existing Enum constraint in `schemas.py`, it backstops it.
   - **Inline free-text citation check:** for every objection/alternative, scan its `text` field for bracket-delimited tokens matching `\[([^\[\]\s]+)\]` (the exact citation convention `prompts.py::build_human_message` already instructs the model to use: `[chunk_id] excerpt ...`) and require every such token to be a member of the retrieved-chunk-ID set for this request. A bracketed token that is not in that set is a fabricated or foreign citation and is a violation (closes gap 2).
   - Each violation is a structured record (which item — objection/alternative, its index, the field — `chunk_ids` or `text`, and the offending value) sufficient to (a) build a corrective message for a regeneration attempt and (b) show up clearly in a test assertion or log line.
2. A bounded reject-and-regenerate loop in `ingestion/critic/service.py::run_critique`: after `generate_critique` returns a structured response, run the validator from item 1.
   - If it passes (no violations), proceed exactly as today (assemble and return `CritiqueResponse`).
   - If it fails, call `generate_critique` again, this time with an additional corrective instruction appended to the human message (built by a new `prompts.py::build_correction_message(violations, valid_chunk_ids)` helper) that names each invalid reference found and reiterates the exact valid `chunk_id` set — then re-run the validator on the new response.
   - Repeat up to `settings.max_regeneration_attempts` additional attempts (see item 3) beyond the first. If every attempt (first call plus all regeneration attempts) still fails validation, raise `CritiqueGenerationError` with a message listing the final attempt's violations — the request still fails closed (never a `200` with an unverified citation), but only after regeneration was actually attempted, closing gap 3.
   - This loop, its attempt count, and every validator call must be visible to a test via dependency injection (the existing `generator` callable in `generate_critique`/`run_critique` already supports returning different values on successive calls — a test-provided fake generator can return an invalid response on call 1 and a valid one on call 2 to prove the retry happened).
3. A new setting `CRITIC_MAX_REGENERATION_ATTEMPTS` in `ingestion/critic/settings.py` (default `2`, meaning up to 3 total generation attempts: 1 initial + 2 regenerations), following the same env-driven dataclass-field pattern already used for `CRITIC_DEFAULT_TOP_K` etc.
4. A `known_ids` parameter shape on the validator (item 1) that today is populated with only the request's retrieved AAR `chunk_id`s, but is written so a future caller can pass an additional set of valid feature IDs (once an impact-JSON producer exists) without changing the validator's interface or rewriting its logic — this is a forward-compatible parameter, not an integration; nothing in this feature reads, fetches, or fabricates a feature ID or impact JSON, per the honest scoping in Problem, item 4.
5. Offline tests:
   - `ingestion/tests/test_critic_validator.py` — unit tests for `validator.py` covering: a fully valid response (no violations); a structured `chunk_ids` entry outside the retrieved set (structural violation, proving the backstop catches what the schema Enum is supposed to already prevent); a bracketed inline citation in `text` that is outside the retrieved set (inline violation); a bracketed inline citation in `text` that *is* in the retrieved set (not a violation — legitimate citation style is not penalized); an empty `objections`/`alternatives` pair (no violations — matches the existing "plan may align with history" behavior).
   - Updates/additions to `ingestion/tests/test_critic_service.py` — a fake `generator` that returns an invalid structured response (a fabricated `chunk_id` or an inline bracketed reference outside the retrieved set) on its first call and a fully valid one on its second call; assert `run_critique` returns the valid, second-call response and that the fake generator was called exactly twice (proving one regeneration occurred, not a silent pass of the first invalid response). A second test where the fake generator returns an invalid response on every call up to `max_regeneration_attempts + 1` total calls; assert `run_critique` raises `CritiqueGenerationError` only after that many calls (proving it fails closed after genuinely exhausting regeneration, not after zero or one attempt).
6. Documentation: extend `ingestion/README.md`'s existing "Historical critic API" section with a subsection describing the validator (what it checks, what it does not check, the regenerate-then-fail-closed behavior) and the new `CRITIC_MAX_REGENERATION_ATTEMPTS` env var; add that var (commented, with its default) to `ingestion/.env.example`.

## Out of scope

- Feature-ID / impact-JSON citation checking. No impact extractor or impact JSON producer exists anywhere in this repository (confirmed by reading every `pipeline/features/*` folder and `historical-critic-api/spec.md`'s own Out of scope). Per Problem item 4, this feature does not fetch, validate, or fabricate a "current flood facts" integration; the validator's `known_ids` parameter is left forward-compatible (item 4, In scope) for whichever future feature implements PRD contract 2, but that integration is not built here.
- RAGAS faithfulness/context-precision/relevance evaluation (FeatureBreakdown step 7; PRD 5, PRD 11). This feature only checks that a referenced `chunk_id` (structured or inline-bracketed) was actually retrieved for the request — it does not check whether the retrieved chunk's content actually supports the claim being made next to it, whether a hazard/phase/tactic/outcome description attributed to a chunk matches that chunk's real analytic fields, or any other semantic faithfulness question. PRD 11 states explicitly that this is a distinct failure mode from citation existence and remains RAGAS's job.
- Changing or removing the existing per-request `Enum` constraint in `ingestion/critic/schemas.py::build_structured_response_schema`. This feature adds an independent second layer on top of it (In scope, item 1's "structural re-check"), it does not replace the first line of defense.
- Any change to `ingestion/aar/` (the corpus/search package) or to the retrieval logic in `ingestion/critic/service.py` beyond adding the regenerate loop around the existing `generate_critique` call. Retrieval itself (query building, `search_index` call, `NoHistoricalContextError` on empty retrieval) is unchanged.
- Rewriting or relaxing any existing error mapping in `ingestion/critic/app.py` (`NoHistoricalContextError` → 422, `aar.models.IndexError`/`RuntimeError` → 503, `CritiqueGenerationError` → 502, unhandled → 500). The new "exhausted regeneration" failure still raises `CritiqueGenerationError` and still maps to the existing 502 handler; no new HTTP status code or route is added.
- Free-text claim scanning beyond the bracketed-citation convention (e.g., detecting an unbracketed prose mention of a document title, a page number, or a numeric outcome claim that doesn't match a chunk). The only rule this feature enforces on free text is the bracket-delimited citation format the system's own prompt already asks the model to use; broader hallucination detection in prose is a faithfulness problem (RAGAS), not an existence-check problem.
- The chat agent, enrichment agent/overlay JSON, search-area tool, historical-decision scorer, session-state persistence, training-mode UI, authentication, rate limiting, or deployment/Docker configuration — all unchanged from `historical-critic-api/spec.md`'s own Out of scope, still untouched here.
- Changes to `src/flood/api` (the physics engine's FastAPI service). This feature only touches `ingestion/critic/`.

## Approach

Add `ingestion/critic/validator.py` as a new, dependency-free module (standard library `re` only) alongside the existing `schemas.py`, `llm.py`, `prompts.py`, `service.py`. It exposes:

```python
@dataclass(frozen=True)
class CitationViolation:
    item_kind: str      # "objection" | "alternative"
    item_index: int
    field: str           # "chunk_ids" | "text"
    value: str            # the offending chunk_id or bracketed token

def find_citation_violations(
    objections: Sequence[dict],   # [{"text": str, "chunk_ids": list[str]}, ...]
    alternatives: Sequence[dict],
    known_chunk_ids: set[str],
) -> list[CitationViolation]: ...
```

`find_citation_violations` iterates every objection then every alternative: for each, every string in `chunk_ids` not in `known_chunk_ids` becomes a `CitationViolation(field="chunk_ids", ...)`; then `re.findall(r"\[([^\[\]\s]+)\]", text)` extracts every bracketed token in `text`, and every token not in `known_chunk_ids` becomes a `CitationViolation(field="text", ...)`. Pure function, no I/O, trivially unit-testable.

`ingestion/critic/service.py::run_critique` changes as follows. After building `response_schema` from the retrieved chunk IDs (unchanged), wrap the existing single `generate_critique` call in a loop:

```python
retrieved_ids = {hit["chunk_id"] for hit in hits}
attempt = 0
last_violations: list[CitationViolation] = []
correction: str | None = None
while attempt <= settings.max_regeneration_attempts:
    structured = generate_critique(
        request.plan, request.situation, request.decision_point, hits,
        response_schema, generator=generator, settings=settings,
        correction=correction,   # new optional kwarg, appended to the human message; None on first attempt
    )
    objections_raw = [{"text": item.text, "chunk_ids": [c.value for c in item.chunk_ids]} for item in structured.objections]
    alternatives_raw = [{"text": item.text, "chunk_ids": [c.value for c in item.chunk_ids]} for item in structured.alternatives]
    last_violations = find_citation_violations(objections_raw, alternatives_raw, retrieved_ids)
    if not last_violations:
        break
    correction = build_correction_message(last_violations, retrieved_ids)
    attempt += 1
else:
    # loop exhausted without ever breaking clean
    raise CritiqueGenerationError(
        f"Historical critique still referenced non-existent chunk IDs after "
        f"{settings.max_regeneration_attempts + 1} attempts: {last_violations}"
    )
```

(Existing exception handling around the `generate_critique` call — catching non-`CritiqueGenerationError` exceptions and wrapping them — is preserved inside this loop; a raw LLM/schema failure on any attempt still wraps immediately into `CritiqueGenerationError` rather than being retried indefinitely, since that is a different failure mode from a citation violation and already fails closed today.)

`ingestion/critic/llm.py::generate_critique` and its default generator gain an optional `correction: str | None = None` keyword-only parameter, threaded into `prompts.py::build_human_message` as an extra trailing section when present (e.g., `"\n\nYour previous response cited something not in the retrieved set: {violations}. Use only the exact bracketed chunk IDs listed above, in both the chunk_ids field and any bracketed reference in your text."`). A caller-injected fake `generator` in tests may ignore this parameter entirely (it is optional and keyword-only, so every existing fake generator signature in `historical-critic-api`'s tests remains valid without modification) or use it to decide what to return on a second call.

`ingestion/critic/prompts.py` gains `build_correction_message(violations: list[CitationViolation], valid_ids: set[str]) -> str`, a small deterministic string builder (no LLM call) that lists each violation's field/value and the full valid ID set, for inclusion in the corrective human message.

`ingestion/critic/settings.py` gains `max_regeneration_attempts: int` (env `CRITIC_MAX_REGENERATION_ATTEMPTS`, default `2`), read with the same `field(default_factory=lambda: int(os.environ.get(...)))` pattern already used for `default_top_k`.

No change to `ingestion/critic/app.py`'s route or exception-handler set: `CritiqueGenerationError` (now potentially raised after multiple attempts instead of one) still maps to the existing `502` handler. No change to `ingestion/critic/schemas.py`'s `build_structured_response_schema` (the Enum constraint stays exactly as-is; this feature backstops it, per Out of scope).

**Why regenerate with a corrective message rather than just re-asking with the identical prompt.** A bare retry without telling the model what was wrong would frequently reproduce the same violation (temperature is already `0` in the default generator). Naming the specific offending value(s) and re-stating the valid ID set gives the retry a concrete chance to self-correct, matching PRD 6.6's "rejected... regenerated" language as an actual corrective loop rather than a coin-flip retry.

**Why the retrieved set, not the whole corpus, is the existence check's ground truth.** Per Problem's framing and the user's own instruction, a `chunk_id` that exists somewhere in the full corpus but was never retrieved for this request was never handed to the model as grounding context — treating it as valid would let the model cite a real-sounding ID it recognizes from elsewhere (training data, a prior request) without ever having seen that chunk's actual excerpt this turn. The retrieved-set check is strictly stronger than a whole-corpus check, and it is what `schemas.py`'s existing Enum already checks — this feature's rule-check reuses the same ground truth for consistency.

## Acceptance criteria

- [ ] `ingestion/critic/validator.py::find_citation_violations` returns an empty list for a structured response whose every `chunk_ids` entry and every bracketed inline `text` token is a member of the given retrieved-chunk-ID set.
- [ ] `find_citation_violations` returns at least one `CitationViolation` with `field="chunk_ids"` when an objection's or alternative's `chunk_ids` list contains a value absent from the retrieved-chunk-ID set (the structural backstop — this must be caught even though `schemas.py`'s Enum is designed to already prevent it, proving the check is independent, not a no-op).
- [ ] `find_citation_violations` returns at least one `CitationViolation` with `field="text"` when an objection's or alternative's `text` string contains a bracketed token (`[SOMETHING]`) that is absent from the retrieved-chunk-ID set, and returns no such violation when every bracketed token in `text` is present in that set.
- [ ] `find_citation_violations` returns an empty list when `objections` and `alternatives` are both empty lists (a plan that aligns with the historical record still passes validation — matches existing "empty is allowed" behavior).
- [ ] In `ingestion/tests/test_critic_service.py`, a test with a fake `generator` returning an invalid structured response (a fabricated `chunk_ids` entry or an out-of-set bracketed `text` token) on its first call and a fully valid one on its second call: `run_critique` returns the second (valid) response, and the fake `generator` is asserted to have been called exactly twice — proving one regeneration actually occurred rather than the first invalid response being silently returned or immediately erroring.
- [ ] In the same test file, a test with a fake `generator` that returns an invalid response on every call: `run_critique` raises `CritiqueGenerationError` only after being called exactly `settings.max_regeneration_attempts + 1` times (default 3 with the default setting) — asserting the call count proves regeneration was genuinely attempted the configured number of times before failing closed, not zero or one.
- [ ] `run_critique` never returns a `CritiqueResponse` whose `objections`/`alternatives` contain a `chunk_ids` entry or a bracketed `text` token outside that request's retrieved-chunk-ID set, under any fake-`generator` behavior exercised in tests (i.e., `find_citation_violations` is actually invoked on every attempt's output before it can be returned, verified by covering both a passing and a failing case per the two tests above).
- [ ] `CritiqueGenerationError` raised after exhausted regeneration still maps to the existing `502` response in `ingestion/critic/app.py` — no new exception type, route, or status code is introduced (verify via an API-level test reusing the exhausted-regeneration fake generator from the service-level test).
- [ ] `settings.py`'s `max_regeneration_attempts` is read from `CRITIC_MAX_REGENERATION_ATTEMPTS`, defaults to `2` when unset, and a test constructs `Settings()` with the env var set to a different value and confirms `run_critique`'s retry count honors it (e.g., set to `0` and confirm exactly 1 total `generator` call before failing closed on a permanently-invalid fake).
- [ ] `cd ingestion && pytest` passes with the new/updated tests included, with no real `OPENAI_API_KEY`, no network access, and no real built FAISS corpus on disk (all retrieval and generation remain faked/monkeypatched, matching the existing test convention in `historical-critic-api`).
- [ ] `ingestion/README.md`'s critic section documents: what the validator checks (structured `chunk_ids` re-check, inline bracketed `text` citations), what it explicitly does not check (feature IDs / impact JSON — no producer exists yet; faithfulness of a citation's content to the claim — RAGAS's job), the regenerate-then-fail-closed behavior, and the new `CRITIC_MAX_REGENERATION_ATTEMPTS` env var with its default.

## Non-goals and constraints

- This is a rule-based, deterministic checker — no LLM call, no network call, no additional embedding/similarity computation. `find_citation_violations` must be implementable and testable with the standard library alone (PRD 6.6/architecture 5.7 describe this as "rule-checking," not a second AI judge; RAGAS, a separate later feature, is where a model-graded check belongs).
- Do not weaken, replace, or remove the existing per-request `Enum` constraint in `schemas.py`. This feature is an additional, independent layer, not a substitute.
- Do not check feature IDs or any "current flood facts" claim. No impact-JSON producer exists anywhere in this repository today; inventing that integration here would violate the explicit instruction under which this spec was written. State this plainly in the README rather than silently omitting it.
- Do not perform faithfulness/relevance checking (whether a real, correctly-cited chunk's content actually supports the claim next to it, or whether a hazard/phase/outcome description attributed to a chunk matches that chunk's real analytic fields). PRD 11 assigns that to RAGAS as a distinct failure mode; conflating the two here would silently expand scope beyond what step 6 asks for.
- Regeneration must be bounded and must fail closed. There is no unbounded retry loop; after `settings.max_regeneration_attempts + 1` total attempts still fail validation, the request errors (existing `502` mapping) rather than ever returning content that failed the rule-check, and rather than retrying forever.
- No new HTTP route, status code, or exception type beyond what already exists in `app.py`. The regenerate loop is an internal change to `run_critique`; the caller-visible contract (endpoint, request/response shape, existing error codes) is unchanged.
- Every existing acceptance criterion and non-goal in `historical-critic-api/spec.md` remains true after this change (e.g., retrieval is still a direct in-process call, `plan` validation still returns 422 before any fake is invoked, empty retrieval still short-circuits before any `generator` call). This feature only adds validation-and-regenerate around the existing single generation call.

## Assumptions

- The bracket-delimited format (`[chunk_id] excerpt ...`) that `prompts.py::build_human_message` already uses to present retrieved chunks to the model is also the format the model uses (or is asked to use, via the corrective message) when it wants to cite a chunk inline in free text. This spec's inline-citation check therefore looks specifically for that bracket convention (`\[([^\[\]\s]+)\]`) rather than attempting general-purpose named-entity or citation-style detection in prose, which would be a much larger, fuzzier problem outside "rule-checking."
- `settings.max_regeneration_attempts` default of `2` (3 total attempts) is not specified by the PRD/architecture/FeatureBreakdown, which name only the reject-then-regenerate behavior, not a bound. This spec picks a small, fixed default so the demo path has a predictable worst-case latency (at most 3 sequential OpenAI calls per `/v1/critique` request) rather than an unbounded retry; it is a documented, adjustable default, not a hard product requirement to re-litigate here.
- The existing `generator` injection point in `llm.py::generate_critique` (already used by every offline test in `historical-critic-api`) is the correct and sufficient seam for testing the regenerate loop — a fake generator can return different values on successive calls (e.g., via a stateful closure or a list of canned responses popped per call) without needing any new test infrastructure.
- No existing caller of `ingestion/critic` outside this repository depends on `generate_critique`'s exact positional/keyword signature in a way that a new optional, keyword-only `correction` parameter would break; per `historical-critic-api/changes.md`, this service has no known external consumer yet (training mode, which would call it, is not built).

## Open questions

- Whether the corrective regeneration message (`build_correction_message`) should also be logged or surfaced to a caller (e.g., in a debug field on `CritiqueResponse`) so a developer can see that a regeneration occurred, versus keeping it purely internal. This spec keeps it internal (no response-shape change) since no acceptance criterion or product doc asks for that visibility; left to whoever integrates training mode against this endpoint to decide if operational visibility into retry counts is needed.
- Whether the inline bracket-citation convention (`[chunk_id]`) is robust enough once a real OpenAI structured-output call is exercised against this service for the first time (per `historical-critic-api/changes.md`'s own residual risk, no real API key/network call has ever been made against this service yet). If a real model turns out not to follow the bracket convention in free text at all, the inline check in this feature would simply find zero bracketed tokens and never flag a violation on that axis — it would not produce false positives, but it also would not catch an un-bracketed inline citation. That would need a follow-up spec once real model behavior is observed; not knowable from static code reading alone.
- Whether `find_citation_violations` should eventually also flag a bracketed token that matches a real, corpus-wide `chunk_id` format but belongs to a *different* AAR document than the one whose excerpt appears nearby in the same objection's text (a "right corpus, wrong context" mismatch) — this is arguably closer to a faithfulness check (RAGAS's job) than an existence check, so this spec does not attempt it, but it is worth flagging as a possible gray area between the two features' responsibilities.
