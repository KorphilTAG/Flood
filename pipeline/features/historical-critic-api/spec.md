# Feature spec

- Slug: historical-critic-api
- Feature: A FastAPI service that takes a trainee's proposed plan, retrieves grounded historical context in-process from the existing `ingestion/aar` LangChain/FAISS corpus, and calls the OpenAI API through LangChain to return cited, historically-grounded critique
- Status: draft
- Product refs: PRD 5 (LLM generation = OpenAI API row), PRD 6.6 (LLM/RAG layer — critic behavior, RAG corpus tool, "every objection citing a chunk ID... never a bare assertion"), PRD 7 principle 3 (every LLM claim cites a real ID), PRD 8 contract 2/3 (impact JSON / overlay JSON — not yet written), PRD 9 Milestone 3 ("LLM critic responds with cited critique at a single decision point"); FeatureBreakdown "RAG + Human/Landscape Data" track, step 5 (this feature) and its stated relationship to step 6 (output validator, explicitly a separate later build "inside the same FastAPI service from step 5"); architecture.md 5.7 (LLM layer, critic behavior, validator) and 5.8 (session state, not yet built); docs/contracts/README.md (contract 2 "Impact JSON" and contract 4 "Session state" both still "To be written in the master spec"); `pipeline/features/historical-flood-report-library/spec.md` and `pipeline/features/langchain-flood-report-library/spec.md` plus their `changes.md` (the already-implemented `ingestion/aar` corpus/search this feature calls); decision 0007 (AAR generator, later consumer of this critic's citation shape, not built here)

## Problem

`ingestion/aar` (implemented in the two prior features) already builds a manually verified, citation-preserving FAISS corpus of Texas flood AARs and exposes it only through `python -m aar search`, a one-shot CLI a human runs by hand. There is no way for anything else in the system — training mode, a future chat agent, a future enrichment agent — to ask "here is what a trainee proposed, what does the historical record say about it" and get back a written, cited answer. FeatureBreakdown's "RAG + Human/Landscape Data" track step 5 names exactly this gap: "Build the AI system that reads a trainee's proposed plan and responds with cited, historically-grounded feedback," using FastAPI to run the logic, OpenAI API to write the response, and the step-4 search as its retrieval tool.

Two upstream contracts this critic would ideally also consume — impact JSON (contract 2, PRD 6.5) and the session state store (contract 4, PRD 8) — do not exist in this repository yet (`docs/contracts/README.md` marks both "To be written in the master spec," and no impact-extractor feature is present in `pipeline/features/`). This feature cannot invent them. It builds the next real layer on top of what exists today — the AAR corpus and search — and takes the trainee's plan plus whatever situational text a caller chooses to supply as opaque input, rather than fabricating a feature-ID-grounded impact-JSON integration that has no producer yet.

## In scope

1. A new, standalone Python package `ingestion/critic/`, run from `ingestion/` the same way `aar` is, exposing a FastAPI app (`create_app()` in `ingestion/critic/app.py`) with:
   - `POST /v1/critique` — accepts a trainee's plan (and optional retrieval filters/context), retrieves AAR context, calls the OpenAI API via LangChain, and returns structured, cited objections and alternatives.
   - `GET /healthz` — liveness only, no external calls.
2. In-process retrieval: the service imports and calls `aar.search.search_index(...)` directly (a Python function call within the same process), never a subprocess call to `python -m aar search` and never re-implementing corpus loading. The corpus/index directory is a configured path (env var, default `data/aar/library`), matching the artifact layout `aar.corpus`/`aar.search` already produce.
3. Retrieval-then-generation orchestration (`ingestion/critic/service.py`): build a retrieval query from the trainee's plan (plus any optional caller-supplied situation/decision-point text), call `search_index` with optional `hazard`/`phase` filters and a configurable `top_k` (default 5), and pass the returned chunk hits — each already carrying `chunk_id`, score, excerpt, citation, and the analytic fields (`hazard`, `phase`, `tactic`, `resources`, `outcome`, `lesson`) — into the LLM call as the only permissible grounding context.
4. LangChain-mediated OpenAI generation (`ingestion/critic/llm.py`): use `langchain_openai.ChatOpenAI` with LangChain's structured-output support so the model's response is parsed into a Pydantic schema, not free text scraped for citations. The schema's citation fields (`chunk_ids` on each objection/alternative) are constrained, per request, to an enum built from exactly the `chunk_id`s retrieved for that request — the model cannot name a chunk ID that was not just handed to it as context. Every objection/alternative item must carry at least one citation (`min_length=1`); the schema itself forbids a bare, uncited claim.
5. A response contract (`ingestion/critic/schemas.py`, `CritiqueResponse`) with: `objections` (list of `{text, chunk_ids}`), `alternatives` (list of `{text, chunk_ids}`), `citations` (the full retrieved chunk records, each with its citation object, so a caller can render/verify without a second search call), and `model` (the OpenAI model actually used). Both `objections` and `alternatives` may be empty lists (a plan can align with the historical record), but any item present must cite real, retrieved chunk IDs.
6. Fail-closed error handling instead of ever returning an ungrounded or fabricated answer:
   - Empty/whitespace `plan` → `422` before any retrieval or LLM call.
   - Retrieval returns zero chunks (corpus built but nothing matches the query/filters) → a `4xx` response stating no historical context was found; the LLM is never called in this case.
   - `aar.search` raises `IndexError`/`RuntimeError` (corpus missing, wrong schema, embedder unavailable) → a `5xx` response surfacing the real cause, not a silent fallback.
   - The OpenAI/LangChain call raises or returns a response that fails schema validation → a `5xx`/`502` response; the failure is surfaced, not passed through as if it were valid critique.
7. Configuration (`ingestion/critic/settings.py`, env-driven, mirroring `src/flood/api/settings.py`'s dataclass-from-`os.environ` pattern): AAR index directory, OpenAI chat model ID (default documented in Assumptions), request timeout, default `top_k`. `OPENAI_API_KEY` is read by the underlying `langchain_openai.ChatOpenAI` client from the environment exactly as `aar.embeddings.load_embedder`'s `openai` provider already does; a missing key fails clearly at call time, not silently.
8. Offline tests (`ingestion/tests/test_critic_service.py`, `ingestion/tests/test_critic_api.py`) using a fake/monkeypatched `search_index` and a fake structured-output LLM call (an injectable generator function, following the same dependency-injection pattern `aar.search.search_index`'s `embedder`/`embedder_factory` parameters already establish) — no real OpenAI API key, no network call, and no real built FAISS corpus required to run `pytest`.
9. Documentation: extend `ingestion/README.md` with how to run the service, the required/optional env vars, and the prerequisite that an AAR corpus must already be built (`python -m aar build`) before this service can answer anything; add the new env vars to `ingestion/.env.example`.

## Out of scope

- The output validator described in PRD 6.6 / architecture 5.7 and FeatureBreakdown step 6 ("Build the safety check that rejects any AI response that references something that doesn't actually exist in the historical library or the current flood facts... built as a rule-checking layer inside the same FastAPI service from step 5"). This feature's per-request structured-output enum (item 4 above) reduces the risk that step 6 addresses but is not that validator: it does not check citations against feature IDs from an impact JSON (that contract doesn't exist yet), it does not re-check citations against the full corpus after the fact, and it never regenerates a rejected response. Step 6 is a distinct, later feature, built into this same service per FeatureBreakdown's own instruction — this spec does not attempt it now.
- RAGAS faithfulness/relevance evaluation (FeatureBreakdown step 7, PRD 5). Structural citation-ID validity (item 4/6 above) is not the same guarantee as "the cited chunk's content actually supports this claim"; that remains RAGAS's job, run separately before trusting outputs in front of a judge or trainee (PRD 11).
- Any dependency on impact JSON, twin feature IDs, or the session state store (PRD 8 contracts 2 and 4; architecture 5.4, 5.8). None of these are implemented anywhere in this repository yet. This feature accepts only the trainee's plan text and optional caller-supplied free-text situation/decision-point context — it does not fetch, validate, or fabricate impact facts, and it never emits or accepts a raw coordinate.
- The enrichment agent and overlay JSON for the 3D map (PRD 6.6, contract 3). That is a different LLM-layer role (produces map markers/polygons keyed to `t`) from the critic role this feature implements (produces a written, cited critique of a proposed plan).
- The chat agent / chatbot tab (PRD 6.6, post-MVP, FeatureBreakdown step 10) and the search-area tool (FeatureBreakdown step 8, architecture 5.6). Neither is touched here.
- The historical-decision scorer (PRD 6.4, PyTorch, stretch/low priority) and any numeric tactic score. This feature returns only the citation-grounded written critique.
- Session-state persistence, training-mode UI, decision-point sequencing/state machine, or any caller-side orchestration across multiple decision points. This is a single stateless request/response endpoint; a future caller (training mode, once built) is responsible for sequencing calls and persisting results.
- Building, validating, or modifying the AAR corpus itself (`ingestion/aar/`). This feature only reads an already-built corpus through `aar.search.search_index`.
- Changes to `src/flood/api` (the physics engine's clock/scenario/run FastAPI service). That is a separate service on a separate track (FeatureBreakdown "Physics Engine"); this feature adds a new, independent FastAPI process rather than editing it.
- Authentication, rate limiting, deployment/Docker/process-manager configuration, and any UI. Out of scope for a hackathon backend endpoint spec.
- Dispatch, evacuation orders, or any operational recommendation framed as an instruction rather than a critique. The human commander remains the decision owner (PRD 2); this endpoint returns objections/alternatives for a human to weigh, never a command.

## Approach

Add `ingestion/critic/` as a sibling package to the existing `ingestion/aar/`, following the same "run from `ingestion/`" convention documented in `ingestion/README.md` and enforced by `ingestion/tests/conftest.py`'s `sys.path` insertion. This keeps the RAG/critic track's code together (per FeatureBreakdown, both `aar` and this service belong to the "RAG + Human/Landscape Data" track) and avoids coupling it to the physics track's installed `flood` package under `src/flood`, which is a separate service on a separate track.

**Request flow.** `POST /v1/critique` accepts a JSON body: `plan` (required, non-empty string — the trainee's proposed tactics in their own words), `situation` (optional string — free text the caller supplies describing what's currently known, e.g. from a training-mode decision point; this service does not fetch or validate it against anything), `decision_point` (optional string label, passed through into the prompt and echoed back for the caller's own logging), `hazard` / `phase` (optional strings, passed straight through as `aar.search.search_index`'s `hazard`/`phase` filters), and `top_k` (optional int, default 5, passed as `search_index`'s `limit`).

`ingestion/critic/service.py` does the orchestration:
1. Validate `plan` is non-empty (FastAPI/Pydantic handles this at the request-model level, returning `422` automatically).
2. Build the retrieval query as `plan` if `situation` is absent, else `f"{situation}\n\n{plan}"` (situation gives context, plan is the primary signal).
3. Call `aar.search.search_index(index_dir, query, hazard=hazard, phase=phase, limit=top_k)` — a direct in-process function call, imported as `from aar.search import search_index` (this only works because both packages are run from/importable relative to `ingestion/`, exactly like the existing CLI). Each hit already has the shape produced by `search.py`: `chunk_id`, `score`, `excerpt`, `citation` (`document_id`, `title`, `publisher`, `canonical_url`, `pdf_sha256`, `page_start`, `page_end`), and the six analytic fields.
4. If `search_index` returns an empty list, raise a typed `NoHistoricalContextError` that the API layer maps to a `4xx` response — never call the LLM with no grounding material.
5. If `search_index` raises `aar.models.IndexError` or `RuntimeError` (missing/incompatible corpus, missing embedder dependency), let it propagate to a `5xx` handler that reports the underlying message — this is a service-configuration failure (the corpus was never built, or was built with a since-removed dependency), not a user input error.
6. Build the per-request structured-output schema: an `Enum` of the retrieved `chunk_id`s, then a `pydantic.create_model`-built response schema (`CritiqueObjection`/`CritiqueAlternative` each with `text: str` and `chunk_ids: list[ChunkIdEnum]` with `min_length=1`, and a top-level model with `objections: list[CritiqueObjection]` and `alternatives: list[CritiqueAlternative]`) — built fresh per request because the valid ID set changes with every retrieval.
7. Call `ingestion/critic/llm.py`'s `generate_critique(plan, situation, decision_point, chunks, response_schema, *, generator=None)`. The default `generator` constructs `ChatOpenAI(model=settings.openai_model, temperature=...)` and calls `.with_structured_output(response_schema)` with a prompt built from `ingestion/critic/prompts.py` (system message: critic role, "cite only the AAR excerpts you were given, by their exact chunk ID; never invent a chunk ID; never issue a dispatch/evacuation order — a human commander decides; if the plan matches historical best practice, `objections` and `alternatives` may be empty"; human message: the plan/situation/decision-point text plus every retrieved chunk rendered as `[chunk_id] excerpt (hazard=..., phase=..., tactic=..., outcome=...)`). Tests inject a fake `generator` so no real `ChatOpenAI`/API key/network call happens offline.
8. Assemble `CritiqueResponse`: the LLM's `objections`/`alternatives` (already enum-validated by the structured-output parse — a schema violation raises before this step, mapped to a `5xx`), plus `citations` built directly from the retrieved chunk dicts (so a caller gets full excerpt/citation detail without a second call), plus `model` (the configured model ID).

**Why a schema-constrained enum, not a post-hoc filter.** Filtering citations after the fact (dropping any `chunk_id` the model invented) would silently produce an under-cited response and mask the model's failure to follow instructions — exactly the failure mode Design Principle 3 exists to prevent. Constraining the JSON schema itself so an invalid ID cannot be represented is cheap (no extra API round-trip, no reject/regenerate loop) and catches the common case; it does not replace the fuller step-6 output validator, which is explicitly a separate, later addition to this same service per FeatureBreakdown.

**Errors.** `ingestion/critic/app.py` maps `NoHistoricalContextError` → `422`, `aar`'s `IndexError`/`RuntimeError` and any LLM/schema failure → `503`/`502` respectively, each as a small JSON body `{"error": {"code": str, "message": str}}` (matching the convention already used by `src/flood/api/errors.py`, for consistency across the two backend services a future UI will call — not a hard dependency on that module, just the same shape). Unhandled exceptions fall through to a generic `500` handler so nothing crashes uvicorn silently.

**Run/test.** From `ingestion/`: `uvicorn critic.app:app --reload --port 8001` (a different port than the physics engine API's default 8000, since both may run locally at once). `cd ingestion && pytest` covers this package fully offline.

## Acceptance criteria

- [ ] `ingestion/critic/app.py` exposes `create_app() -> FastAPI` importable when run from `ingestion/` (matching `aar`'s existing run convention); `uvicorn critic.app:app` starts without a real `OPENAI_API_KEY` or a built corpus present (construction only, no request made yet).
- [ ] `GET /healthz` returns `200` and makes no call to `aar.search` or any LLM client.
- [ ] `POST /v1/critique` with a valid `plan` (with a fake `search_index` returning ≥1 chunk and a fake `generator` returning a valid structured response) returns `200` with `objections`, `alternatives`, `citations`, and `model` present; every `chunk_ids` entry in every objection/alternative is drawn from the `chunk_id`s in `citations`.
- [ ] `POST /v1/critique` with a missing or empty/whitespace-only `plan` returns `422` before the fake `search_index` or `generator` is invoked (assert the fakes recorded zero calls).
- [ ] `POST /v1/critique` where the fake `search_index` returns an empty list returns a `4xx` response naming the lack of historical context, and the fake `generator` records zero calls (the LLM is never invoked without retrieved grounding material).
- [ ] `POST /v1/critique` where the fake `search_index` raises `aar.models.IndexError` (simulating an unbuilt/incompatible corpus) returns a `5xx` response whose body includes the underlying message, not a generic/opaque failure.
- [ ] `POST /v1/critique` where the fake `generator` raises (simulating an OpenAI/LangChain failure or a structured-output parse failure) returns a `5xx`/`502` response rather than a `200` with fabricated content.
- [ ] The per-request structured-output schema passed to the fake `generator` in a service-level test is built from exactly the retrieved chunk IDs for that request (test asserts the schema's allowed citation values equal the fake retrieval's chunk-ID set), and each objection/alternative field in that schema requires at least one citation.
- [ ] Retrieval is a direct Python call (`from aar.search import search_index` or an equivalent in-process import used by `service.py`) — no `subprocess`, `os.system`, or shell-out to `python -m aar search` anywhere in `ingestion/critic/`.
- [ ] `cd ingestion && pytest` passes with the new tests included, without a real `OPENAI_API_KEY`, without network access, and without a real built FAISS corpus on disk (both `search_index` and the LLM `generator` are faked/monkeypatched in every new test).
- [ ] `ingestion/README.md` documents: how to start the service, that `AAR_INDEX_DIR` must point at a corpus already produced by `python -m aar build`, that `OPENAI_API_KEY` is required at request time (not at process start) for a real (non-faked) request, and the `POST /v1/critique` request/response shape.

## Non-goals and constraints

- This is a critic, not a dispatcher. Every returned item is an objection or an alternative for a human commander to weigh, never a machine-issued order (PRD 2, PRD 6.6).
- No raw coordinates in or out. This feature never accepts, computes, or emits a coordinate pair; all geometry remains out of scope because no exposure-layer/feature-ID input is wired to this endpoint yet.
- Every citation this service returns must be a real `chunk_id` present in that request's own retrieval results — never a bare assertion, never an ID invented by the model (PRD 7 principle 3). This is enforced structurally (item 4/6 in Approach), not by post-hoc string matching against free text.
- Do not silently degrade. Every failure mode in Approach/Acceptance criteria returns a clear error rather than a best-effort or partially-grounded answer.
- Do not build the full output validator (existence-check against the whole corpus and current impact JSON, reject-and-regenerate loop) or RAGAS evaluation here; both are explicitly separate, later work per FeatureBreakdown steps 6 and 7.
- Do not add a database, session-state store, or persistence layer. This is a stateless request/response endpoint; the corpus it reads is the file-backed FAISS artifact `aar` already produces (decision 0006 — file-first storage).
- Keep this service and `src/flood/api` (the physics engine's FastAPI app) separate processes; do not import from or edit `src/flood/*` to implement this feature.

## Assumptions

- An AAR corpus has already been built with `python -m aar build` (per the two prior features) at the path this service is configured to read (`AAR_INDEX_DIR`, default `data/aar/library`). This feature does not build, verify, or ship a corpus; it fails clearly (via the `IndexError`/`RuntimeError` path) if none is present when a real request is made.
- The exact OpenAI chat model to use for generation is not pinned by the PRD/architecture docs (PRD 5 names "OpenAI API" generically). This spec treats the model ID as a configurable setting with a documented default (a small, low-latency chat-completions-capable model), to be adjusted by whoever runs the hackathon demo based on latency/cost testing before the event — not a hard product requirement to re-litigate here.
- The retrieval query is built from the trainee's `plan` text (plus optional caller-supplied `situation` text) because no impact JSON producer exists yet to supply that context automatically, per architecture 5.7's intended input ("semantic similarity to the current impact JSON and/or the trainee's proposed plan") — this feature implements the "trainee's proposed plan" half of that sentence today and leaves the impact-JSON half to whichever future feature implements contract 2.
- `langchain_openai.ChatOpenAI`'s `.with_structured_output(...)` can be given a `pydantic.BaseModel` built at request time via `pydantic.create_model` with an `Enum`-typed field, and will honor that enum as the model provider's structured-output/JSON-schema constraint. If the installed `langchain-openai` version's structured-output path does not support a dynamically constructed enum type as expected, the implementer should fall back to validating the LLM's raw `chunk_ids` output against the retrieved set immediately after the structured-output call (still rejecting to a `5xx` on violation, never silently filtering) and note the deviation in `changes.md`; the schema-level enforcement in Approach is the preferred implementation, not the only acceptable one.
- The caller of this endpoint (a future training-mode UI or test harness) is responsible for supplying whatever `situation`/`decision_point`/`hazard`/`phase` context it has; this service does not validate that text against any ground truth, because no such ground-truth source (impact JSON, session state) exists yet in this repository.

## Open questions

- Whether citations should eventually reference twin feature IDs alongside AAR chunk IDs once the impact extractor (contract 2) is built — deferred until that contract exists; this feature only ever cites AAR `chunk_id`s.
- Whether this service and `src/flood/api` should later be merged into one deployable process or stay as two independently run FastAPI apps for the hackathon demo — no decision record covers this; left to whoever integrates training mode against both.
- The production OpenAI chat model, temperature, and token-budget settings for the live demo are not specified anywhere in the PRD/architecture/FeatureBreakdown; left as a configurable default per the Assumptions above rather than guessed here.
