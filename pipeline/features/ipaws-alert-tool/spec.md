# Feature spec

- Slug: ipaws-alert-tool
- Feature: A safe, attribute-only query tool over FEMA's public IPAWS Archive ArcGIS REST table (historical CAP alert records — who alerted whom, when, with what message), for a human curator to use directly when gathering facts to ground a critic claim about actual alert timing/content during a historical event
- Status: draft
- Product refs: PRD 6.1 (AAR corpus row lists "FEMA IPAWS records" as a manual source); PRD 6.6 (critic behavior — "every objection citing a chunk ID or a feature ID, never a bare assertion"); PRD 7 Design Principle 3 (every LLM claim cites a real ID; no invented coordinates); architecture.md 5.5 (AAR pipeline/RAG corpus) and 5.7 (LLM layer, critic behavior, no agent loop implied); FeatureBreakdown "RAG + Human/Landscape Data" track step 4 (FEMA IPAWS records named as one of the manual AAR-corpus documents); `pipeline/features/langchain-datagrabber/spec.md` Out of scope (the critic/enrichment LLM layer is a separate track this feature's sibling ingestion-fetch-layer feature explicitly does not touch, and its `ArcGISFeatureServerTool`/`query_arcgis_feature_server` are scoped to boundary-filtered spatial FeatureServer/MapServer layers); `pipeline/features/historical-critic-api/spec.md` Approach/Out of scope (the critic calls `ChatOpenAI(...).with_structured_output(...)` directly — no `AgentExecutor`, no tool-calling loop — and explicitly does not depend on any new live external data source beyond the AAR corpus and caller-supplied free-text `situation`); `ingestion/aar/models.py` (`REQUIRED_SOURCE_CATEGORIES` includes `"fema_ipaws_records"`) and `ingestion/aar/sources/README.md` (the AAR manifest's curation process requires a text-extractable, page-bounded, human-verified PDF per source — not a raw API record)

## Problem

`ingestion/aar/models.py`'s `REQUIRED_SOURCE_CATEGORIES` already names `fema_ipaws_records` as one of the nine source categories a full AAR corpus needs, and PRD 6.1 lists "FEMA IPAWS records" among the AAR corpus documents that are manually located. Nothing in this repository can currently query that source at all — there is no code path that talks to FEMA's public IPAWS Archive ArcGIS REST service (`https://gis.fema.gov/arcgis/rest/services/FEMA/IPAWS_Archive/MapServer`), and the existing generic ArcGIS wrapper cannot be reused as-is for it.

`ingestion/lib/geo.py::query_arcgis_feature_server` and its LangChain wrapper `ingestion/lib/langchain_tools.py::ArcGISFeatureServerTool` require a `boundary_geojson` polygon and unconditionally send `geometry`/`geometryType`/`spatialRel` params to filter spatially — a design built for TxDOT roads and USGS NHD flowlines, both true spatial FeatureServer layers. The IPAWS Archive's alert-record layer (MapServer layer/table id `1`, `IPAWS_ARCHIVE_EVENTS`) is confirmed, by directly querying `.../MapServer/1?f=json`, to be a **non-spatial ArcGIS Table** — it has no geometry field at all. Sending it a `geometry`/`geometryType`/`spatialRel` filter is meaningless at best and a malformed-request error at worst; the existing tool's input schema (`ArcGISQueryInput`, which requires `boundary_geojson`) cannot even express "no spatial filter." This service needs to be filtered by `sent` (a date range) and `info_area_areadesc` (a free-text, semicolon-separated county/area description field — not a geometry), which the existing tool has no parameter for.

Separately, this alert data is meant to ground a *critic* claim about what alert was actually sent, to whom, and when, during a historical event — for example, the empirically confirmed gap that no alert record in this archive is tagged to Kerr County specifically between 2025-06-12 and 2025-08-04, even though several neighboring counties (Bandera, Comal, Kendall, Burnet, Travis, Williamson) have real Flash Flood Warning records issued by NWS Austin/San Antonio in that same window. `ingestion/critic/service.py` (the already-implemented, merged `historical-critic-api`) is a fixed retrieval-then-generation pipeline: it calls `aar.search.search_index(...)` directly and passes the returned AAR chunks into `ingestion/critic/llm.py::generate_critique`, which constructs `ChatOpenAI(...).with_structured_output(...)` directly. There is no `AgentExecutor`, no tool-calling loop, and no facility anywhere in `ingestion/critic/` for the LLM to decide to call an external tool mid-generation — `historical-critic-api/spec.md`'s Out of scope section is explicit that this service "accepts only the trainee's plan text and optional caller-supplied free-text situation/decision-point context" and does not fetch, validate, or fabricate any new external fact source. Building this feature as an agent-bound tool the LLM invokes on its own would mean introducing exactly the tool-calling architecture that feature's spec deliberately avoided, and would require new structured request fields (an alert area, a date range) on `CritiqueRequest` that do not exist today — a change to an already-reviewed, merged API contract this spec does not make.

This feature therefore builds a standalone, deterministic query capability — a plain Python function wrapped in a LangChain `BaseTool` shape for interface consistency with the ingestion codebase's existing tool convention, invoked directly (`.invoke({...})` or a CLI script), the same way `aar.search.search_index` is called as a direct Python function today. It is a fact-gathering tool a human curator runs to pull real alert records for a date range and area, which they then fold into the critic's existing free-text `situation` input (or hold as manual notes) — not a new automatic input to the critique request/response contract.

## In scope

1. A new module `ingestion/critic/ipaws.py` with:
   - `build_where_clause(start_date, end_date, area_contains=None, event_type=None, status="Actual") -> str` — builds a safe ArcGIS SQL `where` clause from **structured** inputs only. `start_date`/`end_date` must match strict `YYYY-MM-DD` and are rejected (`ValueError`) otherwise, before any string is built. `area_contains`/`event_type`, if given, are matched as `UPPER(...) LIKE '%...%'` substrings against `info_area_areadesc`/`info_event` respectively, with every embedded single quote escaped by doubling (`'` → `''`) so no caller-supplied text can terminate the SQL string literal early. `status` defaults to `"Actual"` (excludes FEMA/CAP `Test`/`Exercise`/`Draft`/`System` records from being mistaken for real alerts); passing `status=None` omits the status filter entirely.
   - `query_ipaws_alerts(start_date, end_date, area_contains=None, event_type=None, status="Actual", max_records=2000, base_url=IPAWS_ARCHIVE_EVENTS_URL, session=None) -> list[dict]` — calls `.../MapServer/1/query` with `where` (from `build_where_clause`), a fixed `outFields` list (see field set below), `f=json`, and paginates with `resultOffset`/`resultRecordCount` when a page returns a full `maxRecordCount`-sized batch (this service's confirmed cap is 2000 rows per request), stopping when a page returns fewer rows than requested or when the `max_records` cap is reached. Converts each record's raw `sent` (an ArcGIS epoch-millisecond integer) into an ISO-8601 UTC string. Returns only the fields listed below — never the full raw schema.
   - `count_ipaws_alerts(start_date, end_date, area_contains=None, event_type=None, status="Actual") -> int` — same `where`-clause construction, `returnCountOnly=true`, returns the integer count (useful for a curator to check whether a query is empty, e.g. reproducing the "zero Kerr County rows in the flood window" finding, before pulling records).
   - Returned field set per record (the practically useful subset, matching what was confirmed live against the service): `identifier`, `sent` (ISO-8601, converted), `status`, `msgtype`, `info_event`, `info_headline`, `info_description`, `info_instruction`, `info_sendername`, `info_area_areadesc`.
   - `IpawsAlertQueryInput` (Pydantic `BaseModel`): `start_date: str`, `end_date: str`, `area_contains: Optional[str]`, `event_type: Optional[str]`, `status: Optional[str] = "Actual"`, `max_records: int = 2000`.
   - `IpawsAlertQueryTool(BaseTool)`: `name = "ipaws_alert_query"`, `args_schema = IpawsAlertQueryInput`, `_run(...)` calls `query_ipaws_alerts` internally and returns its result unchanged — following the same `BaseTool`-with-Pydantic-`args_schema` convention already used by `ingestion/lib/langchain_tools.py`, but living in `ingestion/critic/` (see Approach for why).
2. A CLI script `ingestion/scripts/query_ipaws_alerts.py`, runnable via `python -m scripts.query_ipaws_alerts --start YYYY-MM-DD --end YYYY-MM-DD [--area TEXT] [--event-type TEXT] [--status TEXT|none] [--max-records N] [--count-only]`, for a curator to run directly without booting the FastAPI critic service. Prints the resulting JSON array (or, with `--count-only`, the integer count) to stdout.
3. Offline unit tests `ingestion/tests/test_ipaws.py` (mocking every HTTP call — no real network access, no API key, matching every other test file already in `ingestion/tests/`).
4. `ingestion/README.md` documentation: what the tool queries, its fixed field set, the default `status="Actual"` filter, how a curator invokes it (script or direct `.invoke()`, never through an agent loop, never automatically called by `POST /v1/critique`), and the retention-accuracy caveat below.
5. Stating the retention caveat honestly, in both the module's docstring/comments and the README: the service's own `serviceDescription` metadata claims "latest 6-Month" retention with a 24-hour publish delay — this has been directly verified as **stale/inaccurate** (`MIN(sent)` across the table is 2020-11-01, `MAX(sent)` was 2026-09-04 when checked on 2026-09-05, a multi-year rolling archive, not six months). Neither this spec nor the code it produces should repeat the "6-month" claim as fact, and neither should assert this is a guaranteed permanent archive — FEMA could change or prune retention at any time without updating that description, and nothing built here should be relied on as a durable system of record.

## Out of scope

- **Wiring this tool into `ingestion/critic/service.py`'s automatic per-request flow.** `CritiqueRequest` (`ingestion/critic/schemas.py`) has no `area`/`date_range` field today, and adding one would extend an already-implemented, reviewed, and merged feature's request contract — a separate, later decision (see Open questions), not made here. This feature is invoked directly by a curator/script, exactly like `aar.search.search_index` is called as a direct in-process function today, never through an agentic tool-calling loop.
- **Any `AgentExecutor`, chat-model tool-binding, or LLM-driven tool selection.** `ingestion/critic/llm.py::generate_critique` calls `ChatOpenAI(...).with_structured_output(...)` directly with no tool-calling loop; this feature does not introduce one, and `IpawsAlertQueryTool` is never bound to a chat model anywhere in this spec's scope.
- **Retrofitting `ingestion/lib/geo.py::query_arcgis_feature_server` / `ingestion/lib/langchain_tools.py::ArcGISFeatureServerTool`** to support non-spatial tables. That wrapper's `ArcGISQueryInput` requires `boundary_geojson` and its underlying function unconditionally sends `geometry`/`geometryType`/`spatialRel`; `IPAWS_ARCHIVE_EVENTS` has no geometry field to filter on. This feature adds its own attribute-only query path instead of changing that one, and does not touch `ingestion/lib/geo.py` or `ingestion/lib/langchain_tools.py` at all.
- **Extending `ingestion/aar/manifest.py`'s `SourceDocument`/`SourceManifest` schema** to accept a non-PDF, non-page-bounded raw API record as a citable AAR source. `REQUIRED_SOURCE_CATEGORIES` still lists `fema_ipaws_records`, and `ingestion/aar/sources/README.md` still requires a curator-verified, text-extractable, page-bounded PDF for every category — this tool's JSON output is not that shape, and turning it into one (e.g., rendering a citable snapshot document a curator then verifies and adds to the manifest) is a separate, heavier manual task this feature does not attempt.
- **Persisting alert records to PostGIS or any database**, building a local mirror of the 443,769-row table, or any batch/bulk ingestion pipeline. This is a live, on-demand, bounded query tool, not an ingestion-to-storage pipeline like `map-data-ingestion`.
- **Following the `originalmessage` field's separate OpenFEMA URL** (`https://www.fema.gov/api/open/v1/IpawsArchivedAlerts?...`) to fetch the full raw CAP XML. The already-returned text fields (`info_description`, `info_instruction`, `info_headline`) are sufficient for grounding a timing/content claim; chasing the original CAP XML is a separate, optional future enhancement.
- **Any change to `ingestion/critic/service.py`, `llm.py`, `app.py`, `schemas.py`, `validator.py`, `settings.py`**, or to any file under `ingestion/aar/`, `ingestion/critic_eval/`, `ingestion/lib/`, or `ingestion/db/`. Only the four files in "Files to change" below are touched.
- **Adding this source to `ingestion/scripts/live_smoke_test.py`** (the opt-in live-endpoint smoke script built by `langchain-datagrabber` for TxDOT/NHD/Overpass/TIGER). Left as a natural, low-risk follow-up for whoever next touches that script; not required here since this spec's own facts were already verified live by direct query (see Product refs / Problem).
- Authentication, rate limiting, or API-key handling — the service is confirmed public and unauthenticated; none is added.

## Approach

**Where this lives, and why.** The obvious two homes are `ingestion/lib/` (where the existing ArcGIS/Overpass/TIGER tool wrappers live) or `ingestion/critic/` (the only real consumer). This spec puts it in `ingestion/critic/ipaws.py`, for two independent reasons: (1) `langchain-datagrabber/spec.md`'s Out of scope draws a hard line that "the PRD 6.6 LLM/RAG layer... is a separate, later feature and is not started, extended, or touched here" by the ingestion-fetch-layer track that owns `lib/geo.py`/`lib/langchain_tools.py` — this feature's only consumer is squarely on the other side of that line; and (2) the existing `ArcGISFeatureServerTool` in that file is schema-incompatible with a non-spatial table (it requires `boundary_geojson`), so reusing it would mean changing a tool the datagrabber track owns and tested against real spatial sources, for a use case it was never designed for.

**Safety: structured inputs only, never a raw `where` string.** Every parameter that reaches the SQL-like `where` clause is one of: a strictly-validated `YYYY-MM-DD` date, a substring matched via `LIKE` with quotes doubled, or a fixed enum-like status string. No function in this module accepts a raw, pass-through `where` string — this is the concrete difference between "a safe where clause built from structured inputs" (what this spec builds) and "an injectable SQL string an LLM could construct" (what it explicitly avoids), per the user's own framing of this feature's scope.

**Pagination and the 2000-row cap.** The service's own `maxRecordCount` (confirmed via `.../MapServer/1?f=json`) is 2000. `query_ipaws_alerts` requests pages of up to 2000 rows using `resultOffset`/`resultRecordCount`, and continues fetching subsequent pages only while the previous page returned exactly a full page's worth of rows (a signal there may be more) — stopping as soon as a page returns fewer rows than requested, or once the caller's `max_records` cap is reached (whichever comes first). In ordinary curator usage (a specific event's date range, optionally narrowed by county) the confirmed real-world result sizes are small (41 rows for the full July 3–5, 2025 window across all counties); the pagination path exists so a wider query does not silently truncate at 2000 without the caller knowing, and the `max_records` cap exists so a careless wide query cannot try to pull all 443,769 rows in one call.

**Date field conversion.** ArcGIS REST returns `date`-typed fields (`sent`, and the other date fields not returned by default here) as epoch-millisecond integers in `f=json` responses. `query_ipaws_alerts` converts `sent` to an ISO-8601 UTC string before returning it — returning the raw integer would not be "the practically useful `sent` field," it would be an implementation detail leaking through.

**Field projection.** `outFields` is fixed to the ten-field list in In scope, not `*`. The full schema (confirmed via `.../MapServer/1?f=json`) has dozens of fields (`xmlns`, `restriction`, `resource_*`, `references_*`, `area_altitude`/`ceiling`, etc.) that are not useful for grounding a claim about timing/content and would only add noise a curator has to filter by hand; this tool does that filtering once, centrally.

**How a curator actually uses this.** Run `python -m scripts.query_ipaws_alerts --start 2025-07-03 --end 2025-07-05 --area Kerr` (or call `IpawsAlertQueryTool().invoke({...})` directly in a shell/notebook). Review the returned records (or the empty-result/zero-count case, which is itself a finding — e.g. the confirmed Kerr County gap). Manually transcribe the relevant fact(s) into the `situation` free-text field already accepted by `POST /v1/critique` (`ingestion/critic/schemas.py::CritiqueRequest.situation`) when constructing a training-mode decision point, or into a manual curation note — no code change to the critique endpoint is needed for this usage, since `situation` already accepts arbitrary caller-supplied context text and the critic's citation validator (`ingestion/critic/validator.py`) only checks AAR `chunk_id` citations, not situation-text provenance.

## Non-goals and constraints

- Not an autonomous dispatcher — this tool returns historical alert facts for a human curator or the critic's cited-critique text; it never issues, drafts, or recommends an alert/dispatch action itself (PRD 2).
- No invented coordinates — `IPAWS_ARCHIVE_EVENTS` has no geometry field at all; this tool never emits, accepts, or synthesizes a coordinate (PRD Design Principle 3).
- No uncited LLM claims — this tool is not an LLM and makes no claim itself; it supplies factual grounding material for a human curator to fold into the critic's existing free-text `situation` input, and does not alter how `ingestion/critic/validator.py`'s citation checking works (that validator only checks AAR `chunk_id` citations, unaffected by this feature).
- Physics does physics — untouched; this feature is entirely within the RAG/critic track and touches no physics, rendering, or geometry code.
- Structured inputs only, never a raw SQL string — the safety property this spec is built around (see Approach).
- Do not misstate the source's retention window. Code comments, docstrings, and README text must state the empirically observed range (2020-11-01 through near-present as of 2026-09-05) rather than repeating the service's stale "6-Month" `serviceDescription` claim, and must not assert the archive is permanent — FEMA could change or prune it at any time without notice.
- No API key or authentication is required or added; the service is confirmed public.

## Assumptions

- Base URL `https://gis.fema.gov/arcgis/rest/services/FEMA/IPAWS_Archive/MapServer`, layer/table id `1` (`IPAWS_ARCHIVE_EVENTS`, non-spatial), `maxRecordCount` of 2000, and the full field list are exactly as the user directly verified against the live service (`.../MapServer/1?f=json`) and reported in this task's invocation; this spec does not re-derive them.
- No API key or authentication is required, per the user's direct curl verification.
- ArcGIS REST returns `date`-typed fields (including `sent`) as epoch-millisecond integers under `f=json`; `query_ipaws_alerts` converts them to ISO-8601 UTC strings. If a future response inspection shows a different date encoding (e.g. `datesInUnknownTimezone` interacting differently), the implementer should adjust the conversion and note the deviation in `changes.md`, but the "always return a human-readable ISO-8601 string, never a raw epoch integer" contract itself should not change.
- `resultOffset`/`resultRecordCount` pagination is standard, widely-supported ArcGIS Server REST behavior and is assumed to work against this specific MapServer instance; this has not been separately live-verified beyond the user's confirmed single-page (41-row) example, which never exercised pagination. If a live pagination attempt reveals this specific server rejects or ignores `resultOffset` (a known limitation on some older ArcGIS Server configurations), the implementer should detect a repeated/identical page and fail closed with a clear error ("pagination unsupported by this endpoint; narrow the date range") rather than loop indefinitely or silently return duplicate rows, and should note the deviation in `changes.md`.
- Default `status="Actual"` (excluding CAP `Test`/`Exercise`/`Draft`/`System` status values) is a reasonable default for grounding claims about a real historical event, not a hard product requirement; it is overridable via `status=None` or an explicit value.
- Folding this tool's output into the critic's existing free-text `situation` field (or holding it as a manual curation note) is a sufficient way to satisfy "for use by the critic service to ground claims" given `historical-critic-api`'s already-established, already-merged non-agentic architecture and its explicit exclusion of new automatic live-data dependencies. Formally wiring IPAWS lookups into the `POST /v1/critique` request/response contract (e.g., new `alert_area`/`alert_date_range` fields, automatic retrieval alongside AAR chunks) is a distinct, larger design decision left to a future feature, not attempted here.
- This module's home is `ingestion/critic/` rather than a new top-level package, since it is a single-file utility whose only real consumer is the critic/curator workflow, and creating a new top-level `ingestion/` package for one module was judged to add structure without benefit at this scope.

## Open questions

- Whether a future feature should extend `CritiqueRequest`/`ingestion/critic/service.py` with structured alert-lookup fields so this tool's retrieval runs automatically alongside AAR retrieval, rather than being a curator-run, copy-into-`situation` step. Left open; this spec deliberately does not modify the already-merged `historical-critic-api` contract.
- Whether the `fema_ipaws_records` AAR manifest category (`ingestion/aar/models.py::REQUIRED_SOURCE_CATEGORIES`) should eventually be satisfied by a curator-authored PDF summarizing findings pulled via this tool, or by some other mechanism compatible with `ingestion/aar/manifest.py`'s PDF-based, page-bounded curation process. Left to whoever next curates the AAR corpus; this feature does not change that process.
- Whether `resultOffset`-based pagination is actually honored by this specific ArcGIS Server instance for a query wide enough to exceed 2000 rows has not been live-verified by this spec beyond a 41-row example that never triggered pagination. Flagged as an assumption above; the implementer should confirm with a real wide-range query before relying on the pagination path in front of a judge or trainee.
