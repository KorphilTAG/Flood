# Feature spec

- Slug: citation-quality-eval
- Feature: An offline RAGAS evaluation harness (`ingestion/critic_eval/`) that runs a fixed, curated sample of representative trainee plans through the real `ingestion/critic` service (real retrieval, real OpenAI generation) and scores the resulting citations for *faithfulness* (does the generated claim actually follow from the cited excerpt) and *context precision* (were the retrieved excerpts actually the relevant ones), producing a human-readable report to run before a demo — not a re-check of whether a cited chunk ID exists, which `critic-output-validator` already does.
- Status: draft
- Product refs: PRD 5 (Technology Stack, RAGAS row: "Measures retrieval and generation quality (faithfulness, answer relevancy, context precision, context recall) without requiring hand-labeled ground truth — a practical fit given the small AAR corpus. Not required for the MVP demo itself, but should run before trusting any citation output."); PRD 11 Risks ("Citation integrity depends entirely on the output validator... Note this only checks that a cited ID *exists*; it does not check that the citation is actually *relevant* to the claim being made. Running RAGAS's faithfulness and context precision metrics against a sample of critic outputs before the demo would catch that gap — the validator and RAGAS check different failure modes, and only having one of them is not the same as having both."); FeatureBreakdown "RAG + Human/Landscape Data" track, step 7 (this feature, verbatim: "Test the AI system's citations for quality, not just existence — the safety check in step 6 only confirms a citation is real, not that it's actually the right one for the claim being made. **Tool: RAGAS**, run against a sample of critique outputs before relying on the system in front of a judge or trainee."), and its tool description ("A testing tool built specifically for AI systems that retrieve documents before answering, checking things like 'did the answer actually stick to what the retrieved reports said' and 'were the retrieved reports actually the right ones.' ... lets the team verify, before showing this to a judge or trainee, that the AI's citations aren't just present but genuinely relevant — catching a subtler mistake than the safety check above can catch on its own."); architecture.md §7 (demo script decision points — 1:14 a.m., 2:30 a.m., 4:03 a.m. — used below as the grounded source for the fixed sample set); `pipeline/features/historical-critic-api/spec.md`/`changes.md` (the critic service this feature evaluates, "step 5"); `pipeline/features/critic-output-validator/spec.md`/`changes.md` (the existence-check validator, "step 6," explicitly distinguished from RAGAS by both of its own Out of scope entries and by PRD 11's own language); `ingestion/critic/{schemas,service,llm,prompts,settings,validator}.py` and `ingestion/aar/{models,search}.py` (the actual code read to ground every input/output shape below).

## Problem

Two things already exist and are explicitly *not* what this feature does. `historical-critic-api` built `ingestion/critic`, a FastAPI/LangChain service (`POST /v1/critique`) that retrieves AAR chunks via `aar.search.search_index` and calls OpenAI to produce cited objections/alternatives. `critic-output-validator` then added `ingestion/critic/validator.py`, a deterministic, LLM-free rule-checker that re-verifies every cited `chunk_id` — both in the structured `chunk_ids` field and inline bracketed tokens in free text — was actually a member of that request's own retrieved set, wired into a bounded reject-and-regenerate loop in `service.py::run_critique`.

Both of those checks answer one question: **does the cited ID exist** (in the retrieved set, and per the schema `Enum`, in the corpus at all)? Neither answers a different, harder question the same two docs call out explicitly: **is the cited chunk actually the right evidence for the claim sitting next to it?** A response can cite a perfectly real, perfectly retrieved `chunk_id` and still misrepresent what that chunk says (a faithfulness failure), or the retrieval step itself can hand the LLM chunks that are not actually the most relevant ones for the plan it's critiquing, so even a scrupulously honest LLM only has bad material to work with (a context-precision failure). `critic-output-validator/spec.md`'s own Out of scope section says this outright: "PRD 11 states explicitly that this is a distinct failure mode from citation existence and remains RAGAS's job." PRD 11 names the tool and the two metrics directly, and FeatureBreakdown step 7 (quoted above) is this feature's literal charter.

Two constraints shape what is actually buildable today, and both are the same constraints the prior two critic features already documented and worked around:

1. **No live traffic to sample from.** There is no impact-JSON producer, no session-state store, and no training-mode UI anywhere in this repository (confirmed by re-reading `historical-critic-api/spec.md`'s and `critic-output-validator/spec.md`'s own Out of scope sections, and by there being no such feature folder in `pipeline/features/`). A RAGAS harness cannot "sample real critique outputs" from a live system that doesn't exist yet. The only feasible input is a small, fixed, checked-in set of representative trainee plans, authored against the real, documented Kerr County decision points (architecture.md §7: 1:14 a.m. warning, 2:30 a.m. rising gauge, 4:03 a.m. emergency) — not scraped from a real trainee session, because none exist, and not synthesized by an LLM into open-ended scenarios, which would drift from the one scenario this whole product is grounded in.
2. **RAGAS's relevant metrics are themselves LLM-judged.** Faithfulness and context precision (the two PRD 11 names) work by asking an LLM to judge whether a response's claims are entailed by given context, and whether retrieved context was relevantly ranked. That means this harness, unlike every offline test in `historical-critic-api`/`critic-output-validator`, cannot be run with a faked LLM and still produce a meaningful score — a fake judge would just report whatever the test rigged it to report. Running this harness for real requires a real `OPENAI_API_KEY`, real network access, a real built AAR corpus, and (to make the check meaningful at all) real, non-faked critic generation to score. This is stated plainly here rather than pretended away: this feature is not fully offline-testable end-to-end the way the prior two are. Only the harness's own plumbing (loading the fixed sample set, calling the critic, reshaping a `CritiqueResponse` into RAGAS's input shape, formatting a report) is unit-tested offline; the actual scoring run is a human-operated, pre-demo check, exactly as FeatureBreakdown step 7 and PRD 11 both frame it ("run against a sample of critique outputs before relying on the system in front of a judge or trainee" / "should run before trusting any citation output").

## In scope

1. A new, standalone Python package `ingestion/critic_eval/`, run from `ingestion/` the same convention as `aar` and `critic`:
   - `ingestion/critic_eval/fixtures/sample_plans.json` — a fixed, checked-in set of representative sample inputs (5–8 entries), each shaped as a `critic.schemas.CritiqueRequest` payload (`plan`, optional `situation`, `decision_point`, `hazard`, `phase`, `top_k`). Every entry's `decision_point`/`situation` text is grounded in architecture.md §7's demo script (the 1:14 a.m. flash flood warning, the 2:30 a.m. rising-gauge/camp-egress point, and the 4:03 a.m. flash flood emergency), with at least one plan variant per decision point that is written to align with the documented best practice (e.g., citing the county plan's reconnaissance step) and at least one variant written to plausibly conflict with it (e.g., a delayed-alert plan), so the sample set exercises both an "objections expected" and an "objections may be empty" path. The `plan`/`situation` text itself is authored by whoever implements this feature, clearly labeled in the file's own header comment/README section as illustrative training-scenario text grounded in the real Kerr County timeline, not a transcript of any real trainee session (none exist).
   - `ingestion/critic_eval/dataset.py` — `load_sample_plans(path) -> list[dict]`: reads and schema-validates the fixture (every entry has a non-empty `plan`; raises a clear `ValueError` naming the offending entry on a missing/blank `plan` or a malformed JSON file), returning plain dicts shaped for `critic.schemas.CritiqueRequest(**entry)`.
   - `ingestion/critic_eval/runner.py` — `run_critic_on_samples(samples, settings, *, run_critique=None) -> list[SampleRun]`, where `SampleRun` (a small `dataclass`) carries the original sample dict plus either a successful `critic.schemas.CritiqueResponse` or a captured exception (never lets one sample's failure abort the batch — a corpus/LLM failure on sample 3 must not prevent samples 4–8 from running). `run_critique` defaults to `critic.service.run_critique` (a direct in-process import, matching `historical-critic-api`'s own in-process convention — no HTTP call to a running `uvicorn` process) but is dependency-injectable so offline tests can supply a fake.
   - `ingestion/critic_eval/mapping.py` — `to_ragas_records(runs: list[SampleRun]) -> list[dict]`: a pure function (no LLM, no network) that converts every *successful* `SampleRun` into RAGAS's per-sample input shape (see Approach for the exact field mapping); a `SampleRun` carrying a captured exception is excluded from the returned list and reported separately (see `report.py`), not silently dropped.
   - `ingestion/critic_eval/ragas_eval.py` — `evaluate_records(records: list[dict], settings, *, evaluate_fn=None) -> list[dict]`: builds a RAGAS `EvaluationDataset` of `SingleTurnSample`s from `records`, constructs the LLM judge (`ragas.llms.LangchainLLMWrapper` wrapping a `langchain_openai.ChatOpenAI`, model configurable via `settings.ragas_judge_model`), and calls RAGAS's `evaluate(...)` with the `Faithfulness` and (a no-reference variant of) `ContextPrecision` metrics (see Assumptions for the exact class-name caveat), returning one score dict per input record (`{"faithfulness": float, "context_precision": float}`, `NaN`/`None` on a per-metric scoring failure, not a crash of the whole run). `evaluate_fn` is dependency-injectable (defaults to `ragas.evaluate`) so the result-extraction glue can be unit-tested with a fake return value, without a real API key or network call.
   - `ingestion/critic_eval/report.py` — pure, RAGAS-import-free module: `format_report(sample_runs, records, scores, settings) -> str` (a human-readable table: decision point, plan excerpt, faithfulness score, context-precision score, a `below threshold` flag per `settings.faithfulness_warn_threshold`/`settings.context_precision_warn_threshold`, and a row per excluded/errored sample naming its exception) and `write_report_json(sample_runs, records, scores, path) -> None` (the same data as machine-readable JSON, for archiving a specific pre-demo run).
   - `ingestion/critic_eval/settings.py` — env-driven `Settings` dataclass (mirrors `critic/settings.py`'s pattern): `aar_index_dir` (default shared with `critic`'s own default, `data/aar/library`), `ragas_judge_model` (default documented in Assumptions), `sample_path` (default `ingestion/critic_eval/fixtures/sample_plans.json`), `report_dir` (default `ingestion/critic_eval/reports/`), `faithfulness_warn_threshold` / `context_precision_warn_threshold` (defaults documented in Assumptions — informational flags in the report, not hard gates, per Approach).
   - `ingestion/critic_eval/__main__.py` — CLI entry point, `python -m critic_eval run [--sample-path PATH] [--fail-under-faithfulness F] [--fail-under-context-precision F]`: loads samples, runs the real critic (real corpus, real `OPENAI_API_KEY`), maps to RAGAS records, runs the real RAGAS evaluation (real judge LLM call), prints the report, writes a timestamped JSON report to `settings.report_dir`, and exits non-zero **only** if a `--fail-under-*` flag is passed and any sample's score falls below it (default: report-only, exit `0`, matching the "human reads this before a demo" operational framing — see Approach).
2. Offline tests (`ingestion/tests/test_critic_eval_dataset.py`, `test_critic_eval_runner.py`, `test_critic_eval_mapping.py`, `test_critic_eval_report.py`) covering every pure/injectable piece of the harness above with fakes — no real `OPENAI_API_KEY`, no network call, no real built FAISS corpus, and no real call into `ragas.evaluate` in any of these files.
3. Add `ragas` to `ingestion/requirements.txt` (pinned to a `>=0.2` floor — see Assumptions for why).
4. Documentation: a new "Citation quality evaluation (RAGAS)" section in `ingestion/README.md` covering what this checks (and explicitly, again, what it does not — existence, already covered by `critic-output-validator`), how to run it, the required env vars, the fixed-sample-set rationale and its location, and the fact that a real run requires a real `OPENAI_API_KEY` and a real built corpus, unlike every other test in `ingestion/`; add the new env vars (commented) to `ingestion/.env.example`.

## Out of scope

- Re-checking citation *existence*. That is `critic-output-validator`'s job (the structured `Enum` in `schemas.py` plus `validator.py::find_citation_violations`), already built and unchanged by this feature. This feature only runs on responses that have already passed that existence check (every real `CritiqueResponse` returned by `run_critique` already has), and only asks the *different* question of whether the citation is relevant/faithful.
- Any synthetic/LLM-generated test-plan corpus. Given no live training-mode traffic exists, this spec deliberately uses a small, fixed, human-authored sample set grounded in the real, documented Kerr County decision points (architecture.md §7) rather than an LLM-generated set of arbitrary scenarios, which would drift from the one reference scenario this entire product is built around and would itself need faithfulness-checking against nothing in particular.
- Any dependency on impact JSON, twin feature IDs, the session-state store, or a training-mode UI (PRD 8 contracts 2/4; architecture 5.4/5.8/5.9). None exist in this repository (confirmed by re-reading both prior critic features' Out of scope sections and by there being no such feature folder in `pipeline/features/`). This feature does not fetch, fabricate, or wait on any of them; the fixed sample set (item 1 above) is the only feasible substitute for live traffic today.
- `context_recall` and `answer_relevancy`. PRD 5's tech-stack row lists all four RAGAS metrics (faithfulness, answer relevancy, context precision, context recall) as things RAGAS *can* measure "without requiring hand-labeled ground truth," but PRD 11's actual risk-mitigation instruction — the more specific, actionable ask, and the one FeatureBreakdown step 7 exists to implement — names only faithfulness and context precision. `context_recall` in RAGAS's standard formulation requires a ground-truth reference answer per sample to score against, which this repository has no source for (no real trainee critique transcripts exist to serve as "correct" reference text, and hand-writing one would be exactly the kind of fabricated ground truth PRD 5 says this tool is meant to avoid needing). `answer_relevancy` is a real, no-ground-truth-required metric RAGAS supports, but PRD 11 does not ask for it and it measures a different property (does the response address the plan, not whether its citations are trustworthy) — this spec leaves it as a documented, easy future addition (see Open questions) rather than silently expanding scope beyond PRD 11's explicit ask.
- A CI gate that blocks merges or deploys on RAGAS scores. FeatureBreakdown step 7's own language — "run against a sample of critique outputs before relying on the system in front of a judge or trainee" — describes a pre-demo, human-operated check, not a per-commit automated gate; PRD 5 echoes this ("Not required for the MVP demo itself, but should run before trusting any citation output"). The CLI supports an opt-in `--fail-under-*` exit-code mode (In scope, item 1) for whoever later wants to wire this into CI, but the default behavior is report-only.
- Any change to `ingestion/critic/*` (schemas, service, llm, prompts, settings, validator, app) or to `ingestion/aar/*`. This feature only reads the critic's public `run_critique` function and the AAR corpus's existing search output; it does not modify either.
- Changes to `src/flood/api` (the physics engine's FastAPI service). Unrelated track.
- Any UI, dashboard, or visualization of RAGAS scores beyond the printed table and the written JSON report file. Out of scope for a hackathon evaluation script.
- Building or shipping the AAR corpus itself, or acquiring an `OPENAI_API_KEY`. Both are prerequisites documented in Assumptions, exactly as `historical-critic-api/spec.md` already documents the same prerequisite for its own service.

## Approach

Add `ingestion/critic_eval/` as a sibling package to `ingestion/aar/` and `ingestion/critic/`, run from `ingestion/`.

**Why a fixed sample set, not synthesized traffic.** `run_critique` needs a `plan` (and optionally `situation`/`decision_point`/`hazard`/`phase`) to do anything; nothing upstream of it in this repository currently produces that input automatically (no impact JSON, no session state, no training-mode UI — same gap `historical-critic-api/spec.md`'s own Problem section already documents). The only grounded, non-fabricated source of representative input is the demo script already written down in architecture.md §7, which names three real decision points on the real Kerr County timeline. `ingestion/critic_eval/fixtures/sample_plans.json` is therefore a small, checked-in JSON file — not a live capture, not an LLM-synthesized scenario generator — with each entry's `decision_point`/`situation` text keyed to one of those three moments and its `plan` text authored to be a plausible trainee response at that moment (both a compliant and a non-compliant variant per decision point, so the sample exercises the "objections cite something" path and the "plan matches history, objections/alternatives empty" path `critic/prompts.py`'s own system prompt explicitly allows).

**Why in-process, real generation (not faked, not HTTP).** `historical-critic-api` and `critic-output-validator` both fake the LLM `generator` in their tests, and rightly so — those tests are checking this repo's *own* orchestration logic (retrieval wiring, schema construction, the regenerate loop), which does not require a real model response to verify. This feature checks something categorically different: whether the *actual* OpenAI-generated critique, grounded in the *actual* retrieved AAR excerpts, holds up under an independent LLM judge. Faking either half would make the score meaningless — it would just report whatever the fake was built to report. So `runner.py` calls `critic.service.run_critique(request, settings)` with no `generator`/`search` override by default, which means a real run of this harness requires the same prerequisites `historical-critic-api/spec.md` documents for a real (non-faked) request to that service: a built AAR corpus and a valid `OPENAI_API_KEY`. Calling `run_critique` directly (an in-process Python function call) rather than making an HTTP request to a running `uvicorn critic.app:app` process avoids needing a second running service for this harness to work, and mirrors `historical-critic-api`'s own in-process convention for calling into `aar.search`.

**RAGAS input mapping (per successful `SampleRun`).** RAGAS's per-turn evaluation input (a `SingleTurnSample`, in the class-based API used by RAGAS ≥0.2) needs `user_input`, `response`, and `retrieved_contexts`; this feature maps them as:
- `user_input` = the sample's `situation` and `plan`, joined the same way `critic/service.py::_build_query` already builds the retrieval query (`f"{situation}\n\n{plan}"` if `situation` is present, else `plan` alone) — this keeps the RAGAS judge asking "does this response make sense given the same input the retriever and the LLM both actually saw," not a differently-worded proxy question.
- `response` = every objection's and alternative's `text` field from the `CritiqueResponse`, joined with newlines in list order (objections, then alternatives). This is the actual claim-bearing generated text whose grounding is under test; `chunk_ids` fields themselves are not fed to RAGAS (existence is `critic-output-validator`'s job, not this one).
- `retrieved_contexts` = the `excerpt` field (already truncated to 500 characters by `aar.search.search_index`, per `ingestion/aar/search.py`) of every entry in `CritiqueResponse.citations`, in the order `citations` already lists them. This is a deliberate choice: the *excerpt*, not the full untruncated chunk text from `chunks.jsonl`, is what `critic/prompts.py::_render_chunk` actually put in front of the LLM when it generated the response (`f"[{chunk_id}] {excerpt} (...)"`). Faithfulness has to be judged against what the model actually saw, not against a longer document the model never read; using the full chunk text instead would make an unfaithful-sounding claim look faithful (or vice versa) purely because RAGAS's judge had more material than the critic's own LLM call did. Context precision uses the same `retrieved_contexts` list (all `top_k` retrieved chunks, not just the ones the response happened to cite), since context precision measures whether the *retrieval step* ranked genuinely relevant material highly among everything it handed the LLM — restricting it to only the cited subset would hide a bad retrieval that the LLM simply chose not to draw on.
- No `reference` (ground-truth) field is populated for either metric — the no-reference variants of both `Faithfulness` and (see Assumptions) context precision are the ones used, per PRD 5's own framing ("without requiring hand-labeled ground truth").

**Report, not gate, by default.** `report.py::format_report` prints a plain table (one row per sample: decision point label, a truncated plan excerpt, faithfulness score, context-precision score, and a `below threshold` marker per `settings.faithfulness_warn_threshold`/`context_precision_warn_threshold`) plus a trailing section listing any sample that errored during the critic call (corpus missing, no historical context found, generation failure) with its exception message, so a run against an unbuilt corpus fails loudly and specifically rather than silently reporting zero scores. `__main__.py` writes the same data as JSON to `settings.report_dir` for archiving a specific pre-demo run, and exits `0` unless a `--fail-under-faithfulness`/`--fail-under-context-precision` flag was explicitly passed and a score fell below it — the operational default matches "a person runs this and reads it before a demo," per FeatureBreakdown step 7's own phrasing, while still allowing a stricter CI-style use later without a design change.

**Run/test.** From `ingestion/`, with a built corpus and `OPENAI_API_KEY` set: `python -m critic_eval run`. `cd ingestion && pytest tests/test_critic_eval_dataset.py tests/test_critic_eval_runner.py tests/test_critic_eval_mapping.py tests/test_critic_eval_report.py` runs fully offline with no key/network/corpus required (every LLM- or network-touching call in these four files is injected/faked).

## Acceptance criteria

- [ ] `ingestion/critic_eval/fixtures/sample_plans.json` contains at least 5 entries, each with a non-empty `plan` and a `decision_point` naming one of the three architecture.md §7 Kerr County decision points (1:14 a.m., 2:30 a.m., or 4:03 a.m.), with at least one entry per decision point.
- [ ] `dataset.py::load_sample_plans` returns a list of dicts, one per fixture entry, each constructible as `critic.schemas.CritiqueRequest(**entry)` without a validation error; a fixture entry with a missing or blank `plan` raises a `ValueError` naming the offending entry (index or decision point), verified with a test fixture file containing a deliberately broken entry.
- [ ] `runner.py::run_critic_on_samples`, given a fake `run_critique` that returns a canned `CritiqueResponse` for some samples and raises for others (test-only, offline), returns one `SampleRun` per input sample; the samples after a raising one are still present in the result (proving one failure does not abort the batch), and each `SampleRun`'s captured exception (where present) round-trips through unchanged.
- [ ] `mapping.py::to_ragas_records`, given canned `SampleRun`s: (a) excludes every `SampleRun` carrying a captured exception from its return value; (b) for a successful run, `retrieved_contexts` equals exactly the `excerpt` strings of `CritiqueResponse.citations` in their original order (not the full untruncated chunk text, and not filtered down to only cited `chunk_id`s); (c) `response` equals the newline-joined `text` fields of every objection followed by every alternative; (d) `user_input` equals `f"{situation}\n\n{plan}"` when `situation` is present on the sample, else `plan` alone (matching `critic/service.py::_build_query`'s own logic).
- [ ] `ragas_eval.py::evaluate_records`, given a fake `evaluate_fn` returning a canned result structure (test-only, no real `ragas.evaluate`/network/API-key use), returns one score dict per input record with `faithfulness` and `context_precision` keys; a test asserts the function never imports or calls a real OpenAI/`langchain_openai` client when `evaluate_fn` is supplied.
- [ ] `report.py::format_report`, given canned per-sample score dicts, renders a row per sample including a `below threshold` marker for any score under the configured warn threshold, and a distinct section listing any excluded/errored sample by its captured exception message; `write_report_json` writes valid JSON containing the same per-sample data, verified by reading it back.
- [ ] `cd ingestion && pytest tests/test_critic_eval_dataset.py tests/test_critic_eval_runner.py tests/test_critic_eval_mapping.py tests/test_critic_eval_report.py` passes with no real `OPENAI_API_KEY`, no network access, and no real built FAISS corpus — every LLM/critic/RAGAS call in these four files is injected/faked. (`ragas_eval.py` is imported by its own test, so `ragas` itself must be installed — per requirements.txt — but no network call or API key is exercised.)
- [ ] `python -m critic_eval run` is documented in `ingestion/README.md` as requiring a real built AAR corpus and a real `OPENAI_API_KEY` to produce meaningful scores (both for the critic generation step and for the RAGAS judge step) — this is stated as a genuine departure from every other test/run path in `ingestion/`, not glossed over.
- [ ] `ingestion/README.md`'s new section states plainly, in its own words, that this feature checks faithfulness/relevance and explicitly does not re-check citation existence, pointing at `critic-output-validator` as the feature that already does that.

## Non-goals and constraints

- Do not re-implement or duplicate `critic-output-validator`'s existence check. This feature only ever runs after that check has already passed (every `CritiqueResponse` `run_critique` can return today already satisfies it); it never re-validates `chunk_id` existence itself.
- Do not fabricate ground-truth reference answers to force `context_recall` (or a reference-based `context_precision`) to run. If the installed RAGAS version's only available context-precision metric requires a `reference` field, use its no-reference variant/class instead (see Assumptions); do not invent a "correct" critique text to satisfy a metric's signature.
- Do not synthesize an open-ended, LLM-generated test-plan corpus. The sample set is small, fixed, checked into the repo, and grounded in the specific, already-documented Kerr County decision points — not a scenario generator.
- Do not silently skip a failing sample. A per-sample critic-call failure (corpus missing, no historical context retrieved, generation error) must appear in the report by name/exception, not be dropped without a trace.
- Do not present this as a fully offline-testable feature. The harness's own plumbing is offline-tested; producing an actual score requires a real `OPENAI_API_KEY`, real network access, and a real built AAR corpus, and this must be stated in the README and in this spec without hedging.
- Do not turn this into a hard CI gate by default. Report-first, human-read, matching FeatureBreakdown step 7's own "before relying on the system in front of a judge or trainee" framing; the `--fail-under-*` flags are opt-in only.
- Do not modify `ingestion/critic/*` or `ingestion/aar/*`. This feature only calls `critic.service.run_critique` and reads its return value; it changes neither package.

## Assumptions

- **RAGAS metric API surface.** No document in this repository pins an exact RAGAS version or exact metric class/function names — PRD 5 names the tool and four capability areas generically ("faithfulness, answer relevancy, context precision, context recall"), and PRD 11 names two of them by their plain-English concept ("faithfulness and context precision metrics") without a class name. As of the RAGAS releases this spec was written against, the class-based API (RAGAS ≥0.2) exposes `ragas.metrics.Faithfulness` (no reference required) and a no-reference context-precision metric (named `LLMContextPrecisionWithoutReference` in that generation of the library, alongside a reference-requiring `ContextPrecision`/`LLMContextPrecisionWithReference`); inputs are assembled as `ragas.dataset_schema.SingleTurnSample`/`EvaluationDataset`, and `ragas.evaluate(...)` is called with an LLM wrapped via `ragas.llms.LangchainLLMWrapper`. If the version that actually resolves from `ragas>=0.2` at implementation time uses different class names for the same no-reference concepts (RAGAS's metric-naming has churned across releases), the implementer should use the closest currently-available no-reference faithfulness and no-reference context-precision metrics and record the substitution in `changes.md`, the same way `historical-critic-api/spec.md`'s Assumptions pre-authorized a documented fallback for its own LangChain structured-output uncertainty. What must not change regardless of exact class names: no ground-truth `reference` field is fabricated to satisfy a reference-requiring variant (see Non-goals).
- **RAGAS judge model.** Not specified anywhere in the PRD/architecture/FeatureBreakdown. This spec defaults `settings.ragas_judge_model` to the same small, low-latency chat model `critic/settings.py` already defaults to (`gpt-4o-mini`), on the same "adjust for latency/cost before the live demo" basis `historical-critic-api/spec.md` already established for its own model default — not a hard product requirement to re-litigate here. A separate setting (rather than reusing `CRITIC_OPENAI_MODEL` directly) is used so the judge model can be tuned independently of the critic's own generation model.
- **Warn thresholds.** Not specified anywhere in the product docs. This spec defaults both `faithfulness_warn_threshold` and `context_precision_warn_threshold` to `0.7` (RAGAS scores are `0`–`1`) as an informational, report-only flag — a reasonable, adjustable starting point for "worth a second look before the demo," not a validated product requirement. Whoever runs this before a specific demo should read the actual per-sample scores, not just the pass/fail marker.
- **Sample-set size and authorship.** FeatureBreakdown step 7 says "a sample of critique outputs" without specifying a count. 5–8 fixed entries, hand-authored against the three real, documented decision points, is treated as sufficient for a hackathon-scale pre-demo check; growing the sample set is a documented, low-effort follow-up (see Open questions), not a blocker for this feature.
- **In-process call, not HTTP.** `runner.py` calls `critic.service.run_critique` directly rather than making an HTTP request to a running `uvicorn critic.app:app` instance. This avoids a second running process being a hard prerequisite for this harness and mirrors the in-process convention `historical-critic-api` already established for its own call into `aar.search`; nothing about the RAGAS scoring logic depends on this choice, so a future caller could add an HTTP-based runner without changing `mapping.py`/`ragas_eval.py`/`report.py`.
- **`excerpt`, not full chunk text, is the correct RAGAS context.** `aar.search.search_index` truncates each chunk's `text` to 500 characters as `excerpt` (`ingestion/aar/search.py`), and `critic/prompts.py::_render_chunk` is what actually puts that (truncated) excerpt in front of the generating LLM. This spec treats that as the correct, non-negotiable definition of "the context the response was actually grounded in" for faithfulness purposes — using the longer, untruncated `chunks.jsonl` text instead would judge the response against material it never saw.

## Open questions

- Whether `answer_relevancy` (a real, no-ground-truth-required RAGAS metric not named by PRD 11 but listed generically in PRD 5) should be added as a third scored metric once this harness is running and its first real report has been read — left for whoever runs the first pre-demo evaluation to decide based on whether faithfulness/context-precision alone feel sufficient.
- Whether the fixed sample set (5–8 entries today) should grow once real trainee sessions exist (post training-mode UI), and whether at that point this harness should also support sampling from real logged critique outputs rather than only the fixed fixture — deferred until session-state/training-mode UI exist, per the same "cannot build against a producer that doesn't exist yet" reasoning `historical-critic-api/spec.md` already applied to impact JSON.
- Whether `--fail-under-*` should ever become the default (a hard CI gate) once the sample set and thresholds have been validated against enough real runs to trust a numeric cutoff — left open; this spec's default is report-only, per FeatureBreakdown step 7's own human-in-the-loop framing, and flipping that default is a product decision for whoever owns the demo pipeline once real score history exists.
- Whether context precision should eventually also be computed as a reference-based metric (comparing retrieval ranking against a hand-labeled "these chunks are relevant to this plan" gold set) rather than only the no-reference variant used here — this would require hand-labeling relevance per sample, which is exactly the "hand-labeled ground truth" PRD 5 says RAGAS is meant to avoid needing; noted as a possible, more rigorous future addition rather than attempted here.
